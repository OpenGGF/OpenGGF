# Mutator framework and worked-example blueprint

[Shared roadmap and reconciled decisions](2026-10-07-mod-challenges-blueprint.md).
Research baseline: `develop` commit `09282b17305cb5794e43a26855cd2b9543b4ff5f`, inspected read-only on 2026-10-07. This document records the accepted design; the bounded prototype is being implemented in the [implementation plan](../plans/2026-10-07-mutators-prototype-implementation.md). Later MVP/product gates remain future work. Repository paths below are relative to that tree. Prototype, MVP and polish are completion gates, not calendar estimates.

## Intent and observed starting point

Let a player assemble small, understandable gameplay variations, edit optional sliders/options/checkboxes through common host UI, and rapidly enable or disable prepared mutators. Humans and agents should be able to build a small mod from an executable example and understand exactly when each setting becomes effective. Every enable, disable and option edit declares its own lifecycle scope.

The existing mod system supplies useful foundations, but does not supply this product:

- `docs/modding/index.md` and `docs/modding/content-mods.md` describe restart-loaded, hash-trusted code mods. `ModSubsystem.processCatalog` is final; `mods/code/ModClassLoaderFactory.create` visits only `orderedEnabled()` boot owners. `ModRuntime` freezes loaders, snapshots and descriptors. `EffectiveCatalogPatchEnablement` is explicitly boot-frozen. `Engine.initializeExternalContentAtBoot` installs all of them once. Paths are under `src/main/java/com/openggf/`.
- `ModRuntime.newRegistrationPlan()` does create fresh entrypoints and private `ModContext` transactions for each launch. `game/patch/ModuleResolutionService.prepareLaunch/resolveForLaunchResult` freezes and resolves that plan. This is per-launch registration of boot-known owners, not repository rescan or hot installation. `game/session/WorldSession` pins root/resolved modules and the data source.
- `ModContext.freeze/mutate` poison invalid transactions; `ModRegistrationPlan` is immutable. `ModFaultBoundary.call` records failure, disables the owner/dependent closure for the process and throws a typed abort. General creator effects are not rollback-safe; the next-line subsystem guide explicitly aborts an arbitrary patch-apply failure.
- `mods/ui/ModManagerScreen.applyDraft` saves pending enablement with “Restart to apply”; `PendingModStateEditor.restartRequired` compares against boot state. `ModState.Entry` contains enable/order/hash trust, not per-mutator settings. `SceneStorage` is scene-owned text storage, not a typed host configuration service.
- `GameLoop.stepPresentationFrame` already supports complete speed-up ticks and matching audio, while `step()` remains the deterministic tick. `game/session/GameplayModeContext.registerGameModuleRewindAdapters` supports session-service snapshots. These are implementation seams, not evidence that live mutators already work.

`docs/modding/BACKLOG.md` records hot reload/live apply as parked historical decisions, audited on `next` at `5e0c714e8`; it is not present implementation authority. `docs/architecture/next-line-subsystems.md` and `docs/architecture/mod-api-compatibility.md` describe current contracts. The descriptor `mod-api-release-policy.properties` currently says candidate `0.7.0`, no published baselines. New public types must follow that descriptor, `ModApiVersion` and normalized candidate signature pin together; blueprint publication itself changes none.

## Recommended host contract

These names describe the accepted contract. Consult the implementation plan and creator guide for the shipped candidate subset. Add owner-scoped `ModContext.registerMutator` contributions to the frozen registration plan. A definition contains a stable local key, schema version, required semantic capabilities, enable scope, disable scope, typed options (each with edit scope), atomic groups, prerequisites/conflicts and a session factory. Creators return bounded policy values; they do not receive a general “apply settings to the live world” callback. Keep policy installation, boundary admission and owner provenance engine-internal.

Prepare trusted installed packages independently of whether their mutators are active. Initially, a boot-loaded package may expose many dormant mutators with all activation defaults off; package load/trust remains distinct from the new activation switches. Extending preparation to boot-discovered inactive packages requires an explicit trusted preparation contract, because the current classloader factory omits disabled packages. Never silently execute untrusted registration to populate a settings screen.

Allocate a fresh `MutatorSessionState` per `WorldSession`/future game-container instance, with immutable definition views and injected capability services. Do not store mutable state in `ModSubsystem.PROCESS`, shared module decorators, static settings or globally resolved game services. Existing `SessionManager` currently admits one active world; that limitation need not become the new contract. Tests must instantiate two independent owners. Hardened S3K may later consume these same capabilities; initial delivery requires neither its migration nor speculative Multigame infrastructure.

`src/main/java/com/openggf/game/rules/GameRules.java` remains the immutable stock/donor authority; dynamic policies overlay its semantic owners, never rewrite static rules or dispatch on game/zone/fixture names. Runtime metadata and art use bounded `ModAssetRoot` and typed `LoadOp` through the ROM pipeline; disassemblies supply research only.

### Boundaries and pending values

Recommended definitions:

- **LIVE:** commit immediately before the next forward tick after explicit Resume from the mutator pause menu. Focus regain, silent ROM pause release and frame-step are not configuration commits.
- **LOAD:** commit before a full level assembly or the menu’s explicit full Restart. A genuine full death reload qualifies and must be explained in the UI. Preview loads, checkpoint snapshot restores, editor view swaps and seamless resource handoffs do not. `LevelManager.loadCurrentLevel`, `restartCurrentLevelAfterDeath` and `respawnPlayer` currently share a FULL reload path; add an explicit host load cause rather than infer user intent from a title card or method name.
- **LAUNCH:** commit when opening a new gameplay/container session after launch resolution. Returning to master title and starting a game qualifies; restarting the executable is a separate installation limitation.

Track requested values, boundary-admitted values, effective activation/policy revision, pending reasons and schema/package identity separately. An option can reach its boundary while inactive without running creator gameplay callbacks. A later toggle consumes only admitted values. It must never reconstruct the policy from the complete requested map. New sessions satisfy launch/load boundaries in order; restored worlds restore historical effective values instead.

Atomic groups are opt-in, not a mutator-wide blanket scope. Host capabilities impose minimum safe scopes; reject an unsafe LIVE declaration. The group’s declared scope must cover every member’s minimum scope. A group commits all members or none. On each boundary, freeze a candidate revision, validate ranges/groups/capabilities and the effective dependency graph, prepare every affected contribution, then publish one immutable policy set. An edit dependent on an unadmitted option waits, with a visible reason. Reordering is a configuration operation with its own scope. Required prerequisites cannot be half-enabled, and disable cascades use the effective dependency closure.

Prefer host-defined composition: deny sets union; scatter ceilings take the minimum; dimensionless modifiers multiply then undergo one host bound; exclusive policies conflict visibly unless an explicitly declared ordered composition exists. Preserve owner provenance for every result. Do not adopt silent last-writer-wins for physics or clocks just because patch order already exists. No Rings dominates Ringfall, ring monitors and ring rewards; Stealth may make Big Head visually ineffective, which the UI explains.

Persist requested settings atomically, namespaced by package/mutator identity and game profile, with schema version, stable option IDs and migration history. Effective settings belong to the session, not the settings file. Build bounded parsing and publication on the guarantees exercised by `mods/TestModStateStore`, including write failure and symlink/root identity handling. Use integers/fixed-point serialized values, stable enum tokens, explicit defaults and units; reject NaN, out-of-range and unknown active options. Preserve orphaned settings inertly for uninstall/reinstall. Updates require host-validated migration or an explained reset, and changed code bytes require fresh hash trust. Keep save failure visible and retain a retryable draft; do not pretend that runtime and filesystem publication are one transaction.

### Rewind, replay and faults

Capture effective revision, admitted values, deterministic option events, composition order and any pacing accumulator in the session rewind adapter. Restore those before recreating objects that consult policies. Persisted requested values do not overwrite a historical restore. Resuming historical play follows recorded configuration events; a new explicit edit branches history and generates a new event. Resource-bearing revisions retain leases while history references them.

Prototype/MVP retain the current external-content exclusion for stock traces, deterministic tools and verified time attack; ordinary user recordings with mutators are unsupported until they can pin package/schema/content/configuration identities and record effective boundary events. `RecordingLaunchContext` currently has no mutator configuration. Polished modified-game recordings replay input and configuration events, never physics/aux comparison rows. No mutator reads trace measurements or gains readiness authority through a gameplay hook.

Validation/preparation failures publish no candidate graph. Reuse engine-derived owner fault boundaries; report dependent disablement and stop the affected session on unsafe runtime failure. Do not continue after arbitrary creator code may have changed world state. A user may restart into the surviving graph. Host-controlled declarative policies offer stronger containment than arbitrary JVM code; executable trust is not a hostile-code sandbox.

Fault quarantine and hash-trust revocation are host authority outside rewind: a historical revision cannot resurrect disabled code. History may retain resource leases for inspection, but forward resumption into quarantined callbacks requires a safe new session.

## Installation, activation, update and unload

These are distinct operations. Activation changes a prepared policy revision at its declared boundary. Installation admits a new package/catalog generation; update changes bytecode and schema identity; deactivation removes future effects but cannot refund rings, revive objects or undo damage. Unload closes resources only after session, object, provider, history and replay references retire. JVM classloader close is not proof of garbage collection.

No-restart **first installation** is feasible in principle but unimplemented. A bounded follow-on must explicitly import/rescan, validate bytes and hash trust, snapshot dependencies, construct a new immutable catalog/runtime generation, transactionally register mutator-only contributions and hand that generation to eligible sessions. Existing sessions keep their pinned ordinary patch graph. Refuse replacement of an existing owner or its dependency while referenced; stage updates for a new game launch or executable restart. No watch-folder mutation and no arbitrary hot replacement.

Native-image cannot load arbitrary JVM creator classes; `TestModClassLoaderFactoryNativeGuard` and `TestModManagerScreenNativeGuard` enforce that today. MVP can be JVM-only with honest unsupported rows. Polished native support can ship precompiled semantic policy implementations selected by bounded data-only mutator recipes; that is new host work, not evidence that current reskins implement mutators. JVM-only extension code remains explicitly unsupported on native builds.

## Example portfolio

All examples default disabled. Scope declarations below are recommendations for enable/disable and **every listed option**, not limitations of the framework. `J/` abbreviates `src/main/java/com/openggf/`; `T/` abbreviates `src/test/java/com/openggf/`. Relative complexity includes host work, not merely the small mod’s source size. Acceptance here means future polished-example acceptance, not a test run observed during research.

**Gravity — medium; flight/scripted breadth high.** Enable/disable LIVE. Slider 0.25–2.00, default 1.00; underwater on; leader/all-team target; all edits LIVE. `J/sprites/managers/PlayableSpriteMovement.java#doObjectMoveAndFall/applyGravity/applyUnderwaterAirGravityReduction` and `J/sprites/playable/AbstractPlayableSprite.java#getGravity` own normal `$38`, hurt `$30` and water net `$10` acceleration. Gravity is absent from `J/game/PhysicsProfile.java`; profile decoration alone cannot implement it. Scale the owned base/reduction operations coherently, retaining old-velocity integration, native rounding and reverse-gravity direction. Exclude jump impulse, slopes, death and scripted control. Optional passive-flight checkbox, default off, LIVE, requires `TailsFlightController.updateVertical` and carry adoption; do not scale flap thrust or Knuckles’ distinct glide convergence. Accept dry/water/hurt endpoints, water transitions, reverse gravity, carry release and rewind without resetting velocity; DDZ scripted flight is an explicit exclusion. Relevant tests: `T/tests/WaterPhysicsTest.java`, `T/sprites/managers/TestTailsFlightController.java`, `TestPlayableSpriteMovementTailsFlight.java`.

**Ringfall Manipulator — medium.** Enable/disable, percentage, cap-enabled checkbox and cap-count edits each LIVE; percentage 10–100, default 100; cap off, count 1–32/default 32. Use **stock-scatter basis**, not inventory-loss basis: `B=min(held,32)`, then `N=min(B,max(1,floor(B*p/100)),cap)` for positive inventory; omit cap when off, and zero inventory produces zero. At 100 held/50%, target 16 recoverable rings; at 10%, target 3. All 100 held rings are still lost. Tiny counts round down with a minimum one; allocation shortage can reduce recovery further. `J/level/LevelLostRingSpawnCoordinator.java#queue/processPending` and `J/level/rings/RingManager.java#LostRingPool.spawnLostRings` cap/reserve scatter and handle immediate/deferred inventory clearing. Resolve count before reservation, latch it with the spill and snapshot it. Never delete excess rings afterward or let a zero-spawn return avoid inventory loss. Accept 0/1/5/32/100 holdings, each percentage/cap combination, slot exhaustion, two spills and pause/rewind before deferred spawn. Evidence tests: `T/level/TestLevelLostRingSpawnCoordinator.java`, `T/level/rings/TestLostRingObjectInstance.java`, `TestLostRingRewindGenericRestore.java`. Inventory-basis recovery is rejected for the initial slider because it yields a materially different “10%” result.

**Big Head — high, conditional feasibility.** Enable/disable, head-size 1–2/default 1.5 and leader/all-team edits LIVE. `J/level/render/SpriteMappingPiece.java` contains tile geometry, not anatomical labels; `J/sprites/render/PlayerSpriteRenderer.java#drawFrame/applyDplc` consumes changing ROM banks. Require reviewed per-art/per-frame head masks and neck anchors, including mixed head/body tiles, transformed from resolved ROM pixels. Transform only head pixels after native admission, preserving body, feet, collision and camera. No whole-sprite scale or topmost-piece heuristic. Ball poses without a distinct head retain stock art and are documented; unsupported custom/super/donor art reports unavailable. Accept contact sheets for every advertised frame, flips, DPLC generation, neck join, water palette, priority and expanded terrain clipping, with no doubled original head. `J/graphics/SpritePresentation.java#prepare` freezes generations; `T/graphics/TestSpritePresentation.java` and `T/level/render/TestSpritePieceRendererSatPreparation.java` are relevant guard owners. Existing clipped native-tile rendering is insufficient proof of enlarged-pixel clipping.

**Stealth — medium for selective players.** Enable/disable, target and hide-attached-effects checkbox edits LIVE; default target leader, optional effects off. Hide body and tails; keep shields/dust/trails unless selected. Add semantic subject/attachment tags at draw/creation owners and filter immutable presentations after native SAT admission. Do not use `AbstractPlayableSprite.setHidden`: `shouldRefreshRenderFlagThisFrame` reads it. Tails’ appendage draws separately through `J/sprites/managers/TailsTailsController.java#draw`. Accept identical gameplay state under identical inputs, unchanged enemy targeting/collisions/sound, no tail/blink leaks, isolated teammates and no shader-state leakage into HUD/objects. Test owners: `T/graphics/TestSpritePresentation.java`, `T/level/TestLevelSpritePresentationLifecycle.java`. Stealth wins display composition over Big Head.

**No Powerups / Monitor Filter — medium.** The requested behavior is removal of item monitors, with a checkbox per semantic item type. Enable/disable and every removal checkbox use LOAD: freeze the deny set before full level assembly, omit selected monitor placements without marking them destroyed, and preserve source placement identities so a later qualifying reload can restore eligible monitors. Do not remove a monitor live while a character stands on it. Default the removal set to all monitor contents; expose ring/life, shoes, invincibility, each shield variant, harmful Eggman and super-monitor types explicitly where the game supports them. Unsupported types are visibly unavailable. A level-load removal policy must also cover event-created monitors through their semantic factory/placement owners. Removing a required solid can alter a route; certify affected traversal rather than silently replacing it with reward denial.

Monitor owner methods are S1 `Sonic1MonitorObjectInstance.applyMonitorPowerup`, S2 `MonitorObjectInstance.applyMonitorPowerup` and S3K `Sonic3kMonitorObjectInstance.applyPowerup` under `J/game/<owner>/objects/`; subtype numbers differ. Use those producers to inventory semantic contents, then admit or omit the whole monitor before object creation. Accept each type and all combinations promised by the support table, inverted/event-created monitors, repeated loads, checkpoint/stage returns, route solidity changes, object-slot identity, rewind and inactive stock placement equality. `T/tests/TestMonitorIconTiming.java` checks ordinary monitor timing, while `TestTodo3_MonitorEffects` counting enums is not removal behavior coverage. Optional future **reward-only filtering** could apply LIVE at the grant owner while retaining the solid/icon/timing; name and document it separately so it cannot replace the requested removal behavior.

**No Checkpoints — medium.** Enable/disable LOAD; no options initially. Disable respawn banking and use act-start deaths, retaining decorative post activation and independent stage entry. Separate activation marks, respawn eligibility and stage return-position banks. Own admission/restoration through `J/game/CheckpointState.java#saveCheckpoint`, `J/level/LevelCheckpointCoordinator.java#restoreCheckpointState` and `LevelManager.spawnPlayerAtStartPosition`; S3K `SszCheckpointOps.writeCutsceneStarPost` proves object-only interception is incomplete. Accept an already banked checkpoint becoming ineligible at a qualifying reload/restart, scripted SSZ saves, water/camera/timer/solid state, death and stage returns. Extend `T/game/TestCheckpointStateRewind.java`; route-test script dependencies. Deleting posts is rejected because it couples checkpoint denial to special/bonus access.

**No Rings — medium–high.** Enable/disable LOAD; no options initially. Zero main-level inventory; deny placed, attracted, scattered, monitor, slot/prize and giant-ring rewards. Interior-stage ring puzzles remain playable. Typed acquisition decisions must precede inventory, life thresholds, audio, attraction/sparkles and touch-slot consumption; use placement admission as well as award gates, and load/return restoration policy. `J/level/rings/RingManager.java#collectPlacedRing/collectAttractedRing`, `LostRingObjectInstance.update`, `J/game/sonic3k/Sonic3kRingAwardService.java#giveOne`, `S3kSlotRingRewardObjectInstance` and S2 `RingPrizeObjectInstance.collectRing` show multiple award paths, including direct `LevelState.setRings`. Clearing a counter every frame or overriding only `addRings` loses those semantics. Accept zero-ring damage, every source, shared inventory, threshold lives, attraction, returns and disabled restoration without refunds. `T/level/objects/TestLostRingTouchOrdering.java` guards the ring/hazard ordering that denied pickups must not consume.

**No Special Stages — medium.** Enable/disable LIVE; no options. Gate the semantic entry decision before capture/control locks at S1 giant rings, S2 checkpoint stars and S3K `Sonic3kSSEntryRingObjectInstance.onTouched`, with a final transition-owner defense in `J/level/LevelTransitionCoordinator`. Include Super Emerald/sanctuary challenge entry. Carry an admission token so already permitted fades/interiors finish even after toggling. Preserve the giant ring’s existing conditional 50-ring reward branch; disabling entry does not invent that reward. Accept stock progression, stars, emerald routes, active fades and normal return, independently of No Checkpoints/No Rings.

**No Bonus Stages — medium, separate switch.** Enable/disable LIVE; no options. Gate S3K `Sonic3kStarPostObjectInstance.shouldSpawnBonusStars`, `Sonic3kStarPostBonusStarChild.update` and `requestBonusStageEntry` before used marks; leave banking independent and admitted interiors completable. Accept each bonus variant and all four special/bonus toggle combinations. Existing `T/game/sonic2/objects/TestCheckpointObjectInstanceTimeAttackGate.java` and `T/game/sonic3k/objects/TestSonic3kStarPostObjectInstanceTimeAttackGate.java` provide decoupling precedents. GameLoop-only rejection/provider removal is killed by source evidence: giant-ring entry hides/control-locks the player earlier and can strand them.

**Game Speed — low–medium for speed-up; slow motion high.** Enable/disable, 1–4 speed/default 1 and audio follow-speed/normal edits LIVE. `J/game/GameModule.java#gameplayStepsPerFrame/gameplayAudioPlaybackRate` and `J/GameLoop.java#stepPresentationFrame` support 1–32, whole simulation ticks with continuous audio. Fractional speed uses a session rewindable remainder. Preserve menus, transitions, death, rewind and external movie/trace pacing; reject velocity scaling/global-FPS changes. Accept exact fractional tick budgets at 50/60 Hz, one-shot input, timer progression, audio release and boundary stops; existing `T/TestGameLoop.java#customPresentationPacingPumpsWholeStepsAndStopsAtModeBoundaries` and its continuous-audio tests own this seam. Subunity forward speed is absent: the host always admits at least one tick and audio floors at 1. Slow motion needs zero-step presentations, retained input edges, responsive UI and new audio semantics; it remains outside the default polished support promise until those gates pass.

**Violent Explosions — medium for rebound amplification; radial blast high.** Enable/disable, multiplier 1.5–3/default 1.5, resultant speed cap/default 12 px/tick and include-boss checkbox/default off edits LIVE. Mode edit LOAD; rebound mode initially available. `J/level/objects/EnemyDefeatBounce.java#apply` resolves a Y rebound; amplify that resolved result once, then bound the resultant vector deterministically. Explosion-specific hurt amplification needs semantic damage origin at `AbstractPlayableSprite.applyHurt`, not multiplication of every hazard. `ExplosionObjectInstance` is primarily animation; `HczHarmfulExplosionObjectInstance` has actual timed HURT collision. True radial mode is separate: explicit eligible-blast event, latched radius (editable LIVE), one bounded spatial query, direction/coincident-center rules, shield policy and captured hit set. Exclude decorative boss/capsule bursts; avoid double impulses from bounce plus the same blast. Accept rising/falling/grounded kills, matched touch-region coordinates, cap/overflow, underwater hurt, team targets and exactly-once recreation. Tests: `T/level/objects/TestTouchResponseManager.java#multiRegionEnemyBounceUsesMatchedRegionY`, `T/game/sonic3k/objects/TestHczHarmfulExplosionObjectInstance.java`. The title must explain whether the selected mode amplifies a rebound or produces an outward blast.

## Delivery stages, validation and authoring

**Prototype: prove the contract.** Deliver a JVM-only, boot-prepared small-mod starter, host slider/checkbox/enum UI, per-action scope validator, requested/admitted/effective state, atomic publication and session rewind adapter. Implement dry Sonic Gravity and Stealth in an explicitly advertised S2 slice. Exercise a synthetic fixture with enable LIVE, disable LOAD and one option LAUNCH, plus atomic groups; do not invent production settings just to demonstrate LAUNCH. Completion: edit inactive settings, resume LIVE, defer LOAD/LAUNCH, reject invalid groups/dependencies, recreate/rewind across revisions, contain an owner failure and prove inactive stock identity. Non-goals: installation refresh, universal characters, Big Head, new explosions and modified-game recordings.

**MVP: useful prepared mutators.** Extend semantic adapters to explicitly certified S1/S2/S3K routes; add Ringfall, No Powerups, the two independent stage switches and speed-up, plus water/hurt Gravity and selective team presentation. Deliver persisted schema migration, dependency/composition diagnostics, pause-menu and Mod Manager configuration entry points, keyboard/pad/pointer controls, numeric units, reset-to-default and separate active/pending reasons. Completion requires the advertised behavior matrix and scope-bypass and placement-removal cases below, exact stock-off comparisons and the four S3K checks mandated by AGENTS.md. No Rings/No Checkpoints, all-frame Big Head, radial blasts, slow motion, catalog refresh and code update/unload remain outside MVP. Existing route gaps are recorded, not hidden behind a successful load.

**Polished product: qualify breadth and authoring.** Add No Rings/No Checkpoints after award and checkpoint/stage bank separation; ship curated head masks for advertised stock art and both documented explosion modes after their proof gates. Add presets, conflict explanations, searchable settings, accessibility and validated migration/import/export. Deliver modified-session recordings with pinned identities/events, resource-history retirement and native data-recipe parity for shipped policies. Qualify optional passive flight/carry separately. First-install-without-executable-restart is its own gated runtime-generation work package; ordinary patch hot replacement remains excluded. Support stays explicit by game/donor/character/mode, never “all Sonic behavior”.

Dependency order and likely owners: (1) schema/scope/persistence and contribution preparation in `mods/code`, `mods/validation`, `mods/ui`; (2) per-session state and boundary causes in `game/session`, `GameLoopPauseInput`, `level/LevelManager`; (3) minimal semantic hooks at the portfolio’s movement/ring/reward/entry/presentation owners; (4) examples plus focused rewind/stock-identity coverage; (5) recording identity/events and history leases in `game/recording`, `game/rewind`; (6) masks/radial events/native recipes; (7) isolated catalog-generation admission in `ModSubsystem`, `ModClassLoaderFactory`, `ModRuntime`. Inspect change-based selection before future delivery; shared physics/API/lifecycle changes require normal repository validation and affected trace fixtures, not a claim of proportionate tiny-mod testing.

### Worked authoring and acceptance recipes

The SDK must provide a buildable `example-mutators` package, not only pseudocode: one class per example, tiny schema declarations, all scope metadata, host widgets, named support cells and tests; give humans and agents the same build/validate/package/prepare/activate/restart instructions. Future documentation belongs in the existing `docs/modding` handbook/quickstart/sample structure, with capability tables, migration recipe and troubleshooting codes; the dated architecture document records rejected approaches and kill evidence. Update SDK templates/Javadocs and candidate pins for actual public additions. Do not relabel historical plans as completed work or call the new example a maintained gallery member without its executable gates.

Usable contract recipe (proposed schema, not current `ggfmod` syntax): `violent.mode={bounce,radial}:LOAD`; `violent.multiplier={150..300 percent}:LIVE`; `violent.speedCap={4..24 px/tick}:LIVE`; `enable:LIVE`, `disable:LIVE`. Start active at bounce/150%. Request radial, then 300%, and Resume: effective bounce/300%, radial pending LOAD. Disable and re-enable: still bounce/300%. Only a qualifying full load admits radial; lack of the blast capability rejects it atomically. An atomic multiplier/cap group remains LIVE; grouping mode with them requires LOAD and explicit UI disclosure. This directly tests that one option/toggle cannot launder another option’s pending value.

Playable Ringfall recipe: acquire 100 rings, choose 50% and cap off, Resume, take a stock ring-losing hit: lose inventory to zero, plan 16 scatter rings before allocation. Repeat at 10% with cap two: plan two, retain native scatter movement/timing. Rewind to before the hit, replay the same inputs/configuration event: reproduce count, slots and velocities; changing a slider after spill admission does not rewrite pending rings. Run No Rings alongside it after its LOAD boundary: no acquisition/spill rewards, no extra-life/audio leakage. These instructions become executable scenario tests and documented expected outputs, with ROM prerequisites and skips reported.

## Open decisions and research record

User input materially changes two defaults: whether “Violent Explosions” must prioritize true outward blast over the recommended rebound-first delivery, and whether Game Speed must include slow motion rather than the bounded speed-up product. Recommended defaults otherwise stand: stock-scatter percentage basis, main-level-only No Rings, level-load monitor-removal No Powerups, act-start No Checkpoints, finite declared head-art support and JVM-first MVP. No calendar promise or approval ceremony is needed for these routine choices.

Observed checks: `git rev-parse HEAD` matched the baseline; bounded `rg --files`, `rg -n`, `cat` and `sed` inspections read the cited source/tests/docs. Read-only Python citation validation resolved 35 explicit file paths and 22 cited method names; no placeholders remained. `GIT_OPTIONAL_LOCKS=0 git status --porcelain=v1` was empty. No engine tests, Maven runs, runtime probes, dependency installs or disassembly modifications were performed. Existing test names describe assertions inspected, not observed passes. All new-hook feasibility remains subject to the stated proof gates.

Two delegated investigations covered gameplay hooks and presentation; their substantive evidence is incorporated above. Both completed with no pending work.
