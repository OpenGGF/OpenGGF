# OpenGGF 0.7 Widescreen Completion Plan

**Status:** In progress  
**Release branch:** `next`  
**Implementation branch:** `feature/ai-next-widescreen-completion`  
**Starting `next` head:** `84d9a3761`  
**Primary target:** 400x224 (`WIDE_16_9`)  
**Native invariant:** 320x224 (`NATIVE_4_3`) remains exact

## Outcome

Complete and certify the existing widescreen feature as part of OpenGGF 0.7 without
adding work to the feature-frozen 0.6/develop line. Reuse the reviewed widescreen
behavior by porting it through the current `next` owners; do not merge the divergent
develop-side implementation branch wholesale.

The separate frozen-develop-to-next integration remains independently owned. Final
widescreen integration waits for that work to land, refreshes from the resulting
`next`, and resolves overlap once before release-candidate verification.

## Support contract

| Width | 0.7 treatment |
|---:|---|
| 320x224 | Exact native invariant and regression baseline |
| 352x224 | Supported equivalent using width-derived placement |
| 400x224 | Primary supported widescreen target |
| 528x224 | Best-effort; automated bounds and visual smoke evidence |
| 800x224 | Exploratory; no full-support claim |

Trace comparison remains native-only. Widescreen trace capture changes presentation
dimensions, not trace authority, gameplay state, world boundaries, or timing.

## Delivery lanes

The work is split across isolated Luna-agent worktrees with coordinator-owned
integration and review:

1. **Ordinary presentation:** viewport lifecycle, legal/HUD, selectors, title cards,
   results, diagnostics, titles, credits, and endings.
2. **Special stages:** shared viewport contract; S1, S2, and S3K centered native
   presentation; nested local FBO/state ownership; results and transition handoff.
3. **Scene and object defects:** AIZ fire-curtain cache/ring coverage, ICZ freezer clamp,
   and missing regression evidence for already-width-aware GHZ/AIZ/S2 owners.
4. **Capture and teardown:** logical/physical capture dimensions, native trace isolation,
   semantic AIZ capture, and retry-safe GL/GLFW cleanup.
5. **Coordinator:** documentation, branch refresh, conflict reconciliation, regression
   comparison, independent review, integration, push, and worktree cleanup.

Generic `RenderStateStack`/shared-graphics migration is excluded. Special-stage state
ownership stays local to the relevant renderers. Unrelated lifecycle, sidekick, trace,
and route changes from the reviewed develop-side branch are also excluded.

## Acceptance gates

- Native 320 behavior introduces no new test failure or changed visual/layout command
  in the selected native references.
- 352 and 400 use the same width-derived policy with no preset-specific behavior branch.
- Ordinary UI, HUD, endings, all three special stages, and special-stage results receive
  the live logical viewport before rendering.
- Expanded surfaces fill the viewport; native-authored foregrounds use a centered 320px
  safe area; S2 special-stage H32 content remains centered within that safe area.
- AIZ fire-curtain columns cover the live viewport through the mutation/rising sequence,
  and width-sensitive object clamps/windows use the live viewport without moving ROM
  world boundaries.
- Capture metadata records logical and physical dimensions and cannot make trace replay
  non-native.
- Every certifying run has valid test-session start/end markers, run ID, manifest, and
  log. A red historical baseline is acceptable only when no passing baseline test becomes
  red and no pre-existing failure worsens because of this work.
- Final support wording distinguishes certified 320/352/400 behavior from 528
  best-effort and 800 exploratory coverage.
